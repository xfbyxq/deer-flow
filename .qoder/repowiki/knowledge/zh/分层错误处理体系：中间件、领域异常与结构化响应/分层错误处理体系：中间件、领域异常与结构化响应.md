## 1. 整体架构：三层错误处理

DeerFlow 采用「网关 HTTP 层 → Agent 运行时中间件层 → 领域异常类」的分层策略，将外部可观测的错误（HTTP/LLM/Tool）与内部业务语义（Sandbox/Auth/OIDC）解耦。

- **网关层**：FastAPI 的 `HTTPException` + Pydantic `BaseModel` 作为统一对外错误载体；认证模块使用 StrEnum 枚举错误码，避免硬编码字符串。
- **Agent 运行时层**：基于 LangChain `AgentMiddleware` 的两条关键路径——`wrap_model_call`（LLMErrorHandlingMiddleware）和 `wrap_tool_call`（ToolErrorHandlingMiddleware），在调用链外围统一捕获、重试、降级，不污染业务代码。
- **领域层**：各子系统定义自有 Exception 基类（如 `SandboxError`、`OIDCError`、`UserNotFoundError`），向上抛出结构化异常，由上层中间件或路由转换为 HTTP 响应。

## 2. 核心文件与职责

- `backend/packages/harness/deerflow/sandbox/exceptions.py`：Sandbox 域异常族，`SandboxError` 基类 + NotFound/Runtime/Command/File/Permission 子类，统一携带 details 字典
- `backend/app/gateway/auth/errors.py`：认证错误码枚举 `AuthErrorCode`、JWT 解码失败枚举 `TokenError`、结构化响应模型 `AuthErrorResponse`
- `backend/app/gateway/auth/oidc.py`：OIDC 域异常族，`OIDCError` → `OIDCProviderError` / `OIDCValidationError`，用于 ID token 校验失败
- `backend/app/gateway/auth/repositories/base.py`：仓储层 `UserNotFoundError(LookupError)`，遵循 Python 标准 LookupError 语义
- `backend/packages/harness/deerflow/agents/middlewares/llm_error_handling_middleware.py`：LLM 调用重试/退避/熔断，分类 transient/busy/quota/auth，回退为带 deerflow_error_fallback 标记的 AIMessage
- `backend/packages/harness/deerflow/agents/middlewares/tool_error_handling_middleware.py`：Tool 异常转 ToolMessage(status="error")，保留 GraphBubbleUp 控制流信号，附加 skill 上下文元数据
- `backend/app/gateway/auth/user_provisioning.py`：直接 raise HTTPException 把领域错误映射到 HTTP 状态码

## 3. 设计决策与约定

- 不要裸抛 Exception：领域逻辑应抛出自定义异常（继承自各自基类），让中间件/路由统一处理
- 工具异常必须被 ToolErrorHandlingMiddleware 吞掉：该中间件是 tool 执行链的最内层兜底，任何未捕获的 Exception 都会转为 ToolMessage，保证 run 继续推进而非崩溃
- LLM 异常走 LLMErrorHandlingMiddleware：通过 _classify_error 按模式匹配区分 quota/auth/transient/busy，对 transient 做指数退避重试，超限后返回带 fallback 标记的 AIMessage，前端据此展示友好提示
- 认证错误用枚举而非字符串：AuthErrorCode / TokenError 提供单点维护，配合 token_error_to_code 映射函数，避免散落 if/else
- Sandbox 异常携带 details：所有 Sandbox*Error 构造时接受 details: dict，便于日志聚合与前端诊断
- 控制流信号不被吞：两个中间件都显式 except GraphBubbleUp: raise，确保 interrupt/pause/resume 能穿透

## 4. 开发者规则

1. 新增领域错误先定义异常类（继承对应基类），再在路由/服务中 raise，不要在业务里直接 raise HTTPException
2. 写 Tool 时假设异常会被 ToolErrorHandlingMiddleware 捕获，只需抛出有意义的异常消息即可
3. 依赖第三方 LLM SDK 的异常时，不要自行 try/except；让 LLMErrorHandlingMiddleware 的分类器处理，必要时在 _RETRY_BUDGET_OVERRIDES 中注册例外
4. 认证相关错误一律使用 AuthErrorCode / TokenError 枚举，禁止散落的字符串字面量
5. 需要向用户暴露可操作建议时，优先通过 additional_kwargs 注入结构化字段（如 deerflow_error_fallback），而不是拼接长文本
